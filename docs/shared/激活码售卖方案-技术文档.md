# 激活码售卖方案技术文档

## 1. 文档信息

- **文档名称**：激活码售卖方案技术文档
- **适用产品**：无需持续联网的工具类 App
- **文档目标**：定义激活码售卖、发货、激活、本地授权校验与后台管理的技术实现方案
- **版本**：V1.0
- **日期**：2026-08-14

---

## 2. 技术目标

本系统需要支持以下能力：

1. 用户在网站下单购买激活码；
2. 支付成功后自动生成或分配激活码；
3. 激活码可展示在支付成功页，并通过邮件发送给用户；
4. 用户在 App 中输入激活码完成首次联网激活；
5. 服务端校验激活码状态并绑定设备；
6. 服务端签发 License；
7. App 本地保存 License；
8. App 后续离线校验 License 并允许使用；
9. 后台支持订单、激活码、授权、解绑、吊销等管理能力。

## 4. 核心设计原则

### 4.1 激活码只作为随机凭证

激活码不应包含可被客户端离线推导的业务规则。客户端只做格式校验，不判断激活码是否合法。

激活码有效性由服务端数据库判断。

### 4.2 首次激活必须联网

为保证一个激活码只能绑定一次设备，首次激活必须请求服务端。服务端负责判断激活码是否可用，并完成设备绑定。

### 4.3 后续使用离线校验

激活成功后，服务端向 App 返回签名 License。App 本地保存 License，后续启动时不依赖服务端，直接离线验证签名和授权内容。

### 4.4 服务端私钥签发，客户端公钥验证

服务端使用私钥对 License 进行签名。App 内置公钥，只负责验证 License 签名。

禁止将私钥、对称密钥或可生成授权的密钥放入客户端。

## 5. 核心流程

## 5.1 购买与发码流程

```text
用户访问购买页
  ↓
前端请求创建订单接口
  ↓
后端创建订单，状态为 pending
  ↓
用户跳转支付
  ↓
支付平台回调后端
  ↓
后端校验支付回调签名
  ↓
确认支付成功
  ↓
订单状态更新为 paid
  ↓
生成或分配激活码
  ↓
激活码状态更新为 sold
  ↓
支付成功页展示激活码
  ↓
发送激活码邮件
```

### 关键要求

1. 支付回调必须具备幂等性；
2. 同一订单只能绑定一个激活码；
3. 支付回调重复到达时不能重复发码；
4. 发码失败需要可重试；
5. 激活码生成必须使用安全随机数。

---

## 5.2 App 首次激活流程

```text
用户输入激活码
  ↓
App 校验激活码格式
  ↓
App 生成或读取设备指纹
  ↓
App 请求激活接口
  ↓
服务端校验激活码
  ↓
服务端校验设备信息
  ↓
服务端创建 License
  ↓
服务端使用私钥签名 License Payload
  ↓
服务端返回 License
  ↓
App 保存 License
  ↓
App 进入主功能
```

### 激活接口判断逻辑

1. 激活码不存在：拒绝；
2. 激活码未售出：拒绝；
3. 激活码已吊销：拒绝；
4. 激活码已退款：拒绝；
5. 激活码未激活：允许激活并绑定设备；
6. 激活码已激活且设备匹配：返回原 License 或重新签发；
7. 激活码已激活但设备不匹配：拒绝，并提示换机处理。

---

## 5.3 App 离线启动校验流程

```text
App 启动
  ↓
读取本地 License
  ↓
校验 License 格式
  ↓
使用内置公钥校验签名
  ↓
校验 product_id
  ↓
校验 device_fingerprint
  ↓
校验 expire_at，可选
  ↓
通过：进入主功能
失败：进入激活页
```

## 6. 数据模型设计

## 6.1 orders

订单表。

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no VARCHAR(64) NOT NULL UNIQUE,
  product_id VARCHAR(64) NOT NULL,
  buyer_email VARCHAR(255),
  buyer_phone VARCHAR(32),
  amount_cents BIGINT NOT NULL,
  currency VARCHAR(16) NOT NULL DEFAULT 'CNY',
  payment_provider VARCHAR(64) NOT NULL,
  payment_trade_no VARCHAR(128),
  payment_status VARCHAR(32) NOT NULL DEFAULT 'pending',
  paid_at DATETIME NULL,
  refunded_at DATETIME NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX idx_orders_buyer_email (buyer_email),
  INDEX idx_orders_payment_trade_no (payment_trade_no)
);
```

### payment_status 枚举

```text
pending
paid
cancelled
refunded
failed
```

---

## 6.2 activation_codes

激活码表。

```sql
CREATE TABLE activation_codes (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  code_hash VARCHAR(128) NOT NULL UNIQUE,
  code_suffix VARCHAR(16) NOT NULL,
  product_id VARCHAR(64) NOT NULL,
  order_id BIGINT NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'unsold',
  sold_at DATETIME NULL,
  activated_at DATETIME NULL,
  revoked_at DATETIME NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX idx_activation_codes_order_id (order_id),
  INDEX idx_activation_codes_product_id (product_id),
  INDEX idx_activation_codes_status (status)
);
```

### 说明

1. 数据库中建议存储激活码哈希，不存储完整明文激活码；
2. `code_suffix` 用于后台客服模糊识别；
3. 明文激活码仅在生成、展示、邮件发送时短暂出现；
4. 如果业务上必须支持明文找回，则需加密存储，而不是明文存储。

### status 枚举

```text
unsold
sold
activated
revoked
refunded
```

## 8. License Payload 设计

### 8.1 Payload 示例

```json
{
  "license_id": "lic_123456",
  "product_id": "app_pro_lifetime",
  "activation_code_id": "ac_123456",
  "device_fingerprint_hash": "sha256:xxx",
  "features": ["pro"],
  "issued_at": "2026-08-14T12:00:00Z",
  "expire_at": null,
  "license_version": 1
}
```

### 8.2 签名算法建议

推荐使用以下非对称签名算法之一：

1. Ed25519；
2. ECDSA P-256；
3. RSA-PSS 2048 或以上。

MVP 推荐使用 **Ed25519**，原因是签名短、性能好、实现简单。

### 8.3 客户端校验要求

客户端启动时必须校验：

1. License Payload 是否存在；
2. 签名是否有效；
3. `product_id` 是否匹配当前 App；
4. `device_fingerprint_hash` 是否匹配当前设备；
5. `expire_at` 是否未过期；
6. `license_version` 是否支持。

## 9. 激活码生成方案

### 9.1 格式建议

```text
XXXX-XXXX-XXXX-XXXX
```

字符集建议去除易混淆字符，例如：

```text
ABCDEFGHJKLMNPQRSTUVWXYZ23456789
```

避免使用：

```text
0 O 1 I L
```

### 9.2 生成要求

1. 使用安全随机数生成；
2. 激活码长度应具备足够熵；
3. 生成后进行唯一性检查；
4. 数据库存储哈希值；
5. 明文只在发放环节出现。

### 9.3 示例伪代码

```pseudo
charset = "ABCDEFGHJKLMNPQRSTUVWXYZ23456789"
code = random_string(charset, 16)
formatted_code = group(code, 4, "-")
code_hash = sha256(server_pepper + formatted_code)
save(code_hash, suffix)
```

## 10. 设备指纹设计

### 10.1 设计原则

1. 不依赖单一硬件标识；
2. 避免采集过多敏感信息；
3. 对系统升级、轻微硬件变化具备一定容错；
4. 服务端只存储哈希值；
5. 客户端需要稳定生成。

### 10.2 可选因子

可根据平台选择以下因子：

1. 操作系统机器 ID；
2. 主板序列号；
3. 磁盘序列号；
4. CPU 信息；
5. App 本地生成并持久化的设备 ID；
6. 用户系统账户信息的哈希值。

### 10.3 MVP 建议

MVP 阶段建议采用：

```text
App 本地随机生成 device_id + 系统机器 ID
```

然后计算：

```text
device_fingerprint = sha256(app_device_id + os_machine_id + product_id)
```

## 11. 安全设计

### 11.1 服务端安全

1. 支付回调校验签名；
2. 激活接口限流；
3. 找回接口限流；
4. 管理后台鉴权；
5. 高危操作二次确认；
6. 操作日志不可删除；
7. 私钥使用 KMS 或安全配置管理；
8. 数据库不存储完整明文激活码。

### 11.2 客户端安全

1. 不内置私钥；
2. 不内置激活码生成规则；
3. 不使用简单本地开关作为授权依据；
4. 本地 License 文件可加密或混淆存储；
5. 校验失败时回到激活页；
6. 对核心授权逻辑进行基础混淆，可选。

### 11.3 风险边界

该方案可以有效防止普通用户复制安装包、共享激活码、重复激活，但不能保证绝对防破解。任何运行在用户设备上的客户端软件，都存在被逆向、Patch 或 Hook 的可能。

## 12. 幂等与并发控制

### 12.1 支付回调幂等

同一支付交易号可能多次回调，因此需要：

1. 以 `payment_trade_no` 建唯一索引；
2. 发码逻辑加事务；
3. 同一订单已发码时直接返回成功；
4. 避免重复生成激活码。

### 12.2 激活接口并发

同一激活码可能被多个客户端同时提交，因此需要：

1. 使用数据库事务；
2. 对激活码行加锁；
3. 检查状态后再更新；
4. 保证只有一个设备绑定成功。

伪逻辑：

```pseudo
begin transaction
code = select * from activation_codes where code_hash = ? for update
if code.status == 'sold':
    create license
    update code.status = 'activated'
commit
```

## 17. 测试用例

8. License 被篡改后无法通过校验；
9. 设备不匹配时无法进入 App；

## 19. 技术结论

本方案采用“支付成功发码 + 首次联网激活 + 服务端签名 License + 客户端离线验证”的技术架构。该架构可以在较低服务器成本下，实现工具类 App 的商业授权、激活码一次性使用、设备绑定和后续离线使用，是适合 MVP 和后续商业化扩展的技术方案。
